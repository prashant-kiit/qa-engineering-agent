# Tester coverage note — `p0-design-note`

Doc-only unit. Acceptance is a **presence check**: required text must exist in `DESIGN.md §15`.
No test framework exists yet (this unit precedes `p0-scaffold` / Playwright), so the fitting
lightweight runnable mechanism is a self-contained bash assertion script (per `.harness/backlog.md`:
"the Tester encodes their acceptance as presence/smoke checks").

## Test files created
- `tests/docs/design-note.test.sh` — runnable presence/regression test. Exit 0 = all pass, exit 1 =
  any acceptance check failed. `bash tests/docs/design-note.test.sh`.
- `tests/fixtures/design-headings-baseline.txt` — snapshot of all `## ` headings (for C7).
- `tests/fixtures/design-section15-bullets-baseline.txt` — snapshot of pre-existing §15 bullets
  (for C6). Both fixtures were generated by piping from `DESIGN.md` into files **without** the
  content being read into the Tester's reasoning, to lock the "additive only" invariant unbiasedly.

## Acceptance criterion → test mapping
| Criterion | Test check(s) | Red now? |
|---|---|---|
| 1. `## 15. Open / deferred items` heading present/unchanged | C1 | pass (invariant preserved) |
| 2. Note designates scope post-v1 **and** "not in first SaaS release" | C2a, C2b | **RED** |
| 3. Note references (a) auth beyond Basic Auth, naming **SSO/MFA** | C3a, C3b (scoped to the post-v1 note paragraph) | **RED** |
| 4. Note references (b) data residency & retention policy per tenant tier | C4 (scoped to the note paragraph) | **RED** |
| 5. Note states other §15 items implemented in-phase; only fine detail / eval-driven choice deferred | C5a, C5b | **RED** |
| 6. Additive — no pre-existing §15 bullet removed | C6 (vs bullets baseline) | pass (invariant preserved) |
| 7. Well-formed Markdown; no broken/duplicated headings | C7a (heading set == baseline), C7b (no dupes) | pass (invariant preserved) |

Notes:
- C3/C4 are scoped to the **post-v1 note paragraph** (the paragraph containing a `post-v1` phrase),
  not just anywhere in §15 — items (a)/(b) are already mentioned elsewhere in §15, so a section-wide
  grep would not truly verify the note. Scoped to the note, they are legitimately red now.
- C1/C6/C7 are invariants that are already true and that the additive change must preserve; they
  correctly pass at red. The suite as a whole is red (exit 1) for the right reason: the new post-v1
  note (C2–C5) does not yet exist. Failures are behavioral, not scaffolding — verified by a green
  run against a sandbox copy containing the spec's reference wording.
